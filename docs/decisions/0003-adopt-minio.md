# ADR-0003: MinIOでArtifact本体を保持する

## Status

Accepted (2026-09-04)

## Context

生成される成果物には動画（数十〜数百MB）、音声、画像が含まれる。
前身repoはこれをローカルファイルシステム上のディレクトリ
（`content/`、`uploaded/`、約540MB）に置き、パスを文字列でDBやJSONに散らしていた。

問題:
- パスがコードと設計書の散文の両方に書かれ、片方だけ変わって壊れた
- workerがローカルFS前提なので、workerを別ホストへ分散できない
- 同じ成果物を上書きしていたため、「どの素材からどの動画が作られたか」が失われた

## Decision

**MinIO（S3互換オブジェクトストレージ）にArtifact本体を保持する**（INV-9）。
PostgreSQLは参照（bucket / key / sha256 / size）とメタデータのみを持つ。
キーは content-addressed とし、オブジェクトは上書きしない（INV-11）。

## Alternatives

**(a) ローカルファイルシステムを継続** — 単純で速い。しかしworkerを
複数ホストへ分散できず、コンテナ間で共有ボリュームが必要になる。
そもそも「1台が落ちても止まらない」という要件と相性が悪い。却下。

**(b) PostgreSQLのBYTEA / Large Object に格納** — 参照整合性が完璧になる。
しかし数百MBのバイナリをDBに入れると、バックアップ・レプリケーション・
接続バッファのすべてが破綻する。却下。

**(c) AWS S3 を直接使う** — 本番ではこれが望ましい。しかしローカル開発と
CIがネットワークと課金に依存してしまう。**MinIOはS3 APIなので、
本番でS3に差し替えるのはエンドポイント設定の変更で済む** — この可逆性が決め手。

**(d) NFS / 共有ボリューム** — 分散はできるが、content-addressedな
不変オブジェクトという意味論をFSの上に自作することになる。却下。

## Consequences

**良い側**
- workerがステートレスになり、任意のホストで動かせる
- content-addressedなので、同じ入力から同じキーが出る＝再開判定が単純になる
- 本番でAWS S3へ移行するコストが低い（S3互換API）
- バージョン付き成果物を安全に並存させられる

**悪い側 / 引き受けた負債**
- ローカル開発に MinIO コンテナが増える
- **DB行と実オブジェクトの整合を自分で保つ必要がある。**
  2フェーズコミットは無いので、書き順を MinIO → DB に固定し、
  MinIO側の孤児オブジェクトはGCで回収する運用を引き受ける
- immutable運用はストレージを食う。`superseded` 成果物の保持期間ポリシーが
  いずれ必要になる（未決。Phase 2以降の課題）
- ローカルFSに比べレイテンシとAPI呼び出しのオーバーヘッドがある。
  大きな動画のrender中間ファイルは一時ディレクトリで扱い、
  最終成果物だけMinIOへ置く方針とする
